# lkdr-api — пакет изменений

Этот ZIP содержит комплект, который получает полный исходный проект `jfk9w-go/lkdr-api` из GitHub и накладывает изменения.

## Что меняется

- Убирается зависимость примера от RuCaptcha.
- CAPTCHA вводится вручную только если библиотеке действительно понадобится новая авторизация.
- Существующий `tokens.json` с плоской структурой читается без повторного входа.
- Файл токенов и экспорт JSON создаются с правами `0600`, каталог — `0700`.
- Поддерживаются два телефонных аккаунта в одном запуске; второй запускается последовательно после первого.
- Токены хранятся независимо по номеру телефона в одном защищённом JSON-файле.
- Экспорт возобновляется с существующего JSON: уже загруженный список не запрашивается повторно, а чеки с полученными подробностями пропускаются.
- При незавершённой загрузке списка страницы перечитываются с начала, а записи дедуплицируются по `receipt.key`.
- Для каждого запроса подробностей установлен тайм-аут 60 секунд.
- Чеки загружаются страницами по 50 записей до `hasMore=false`.
- Дубликаты удаляются по `receipt.key`.
- Для каждого чека запрашиваются подробности `FiscalData`.
- Экспорт сохраняется после каждой страницы и каждого чека, чтобы не потерять уже полученные данные.
- Добавлен `update_lkdr_token.py` для обновления access-токена из HAR Firefox.

## Установка на FreeBSD

Распакуй ZIP. Перейди в распакованный каталог и запусти:

```sh
sh ./install.sh "$HOME/lkdr-api"
```

Скрипт клонирует полный upstream-проект в указанный каталог, применит overlay и выполнит `go mod tidy`.

## Запуск

Задай переменные окружения:

```sh
export LKDR_PHONE="твой_телефон"
export LKDR_TOKENS_FILE="$HOME/.local/share/lkdr/tokens.json"
export LKDR_DEVICE_ID="твой_sourceDeviceId"
export LKDR_USER_AGENT="строка navigator.userAgent из Firefox"
export LKDR_OUTPUT_FILE="$HOME/receipts.json"

# Необязательно: второй номер
export LKDR_PHONE_2="+7XXXXXXXXXX"
export LKDR_DEVICE_ID_2="$LKDR_DEVICE_ID"       # если отличается — укажи свой
export LKDR_USER_AGENT_2="$LKDR_USER_AGENT"     # если отличается — укажи свой
export LKDR_OUTPUT_FILE_2="$HOME/receipts_phone2.json"
```

Затем:

```sh
cd "$HOME/lkdr-api"
go run ./example
```

Каждый телефон — отдельный аккаунт с собственной сессией. При первом запуске для номера, которого ещё нет в файле токенов, программа должна пройти отдельную авторизацию: CAPTCHA и SMS-код вводятся для этого номера. Первый телефон не авторизует второй автоматически.

Для каждого номера в `LKDR_TOKENS_FILE` должны храниться собственные `token` и `refreshToken`. Не копируй токены первого номера во второй аккаунт и не создавай запись второго номера только из access token: если `refreshToken` пуст, обновление сессии завершится ошибкой `validation.failed (Пустой refreshToken)`.

После успешной авторизации структура файла будет phone-keyed, например:

```json
{
  "+7XXXXXXXXXX": {
    "token": "ACCESS_TOKEN_1",
    "refreshToken": "REFRESH_TOKEN_1"
  },
  "+7YYYYYYYYYY": {
    "token": "ACCESS_TOKEN_2",
    "refreshToken": "REFRESH_TOKEN_2"
  }
}
```

Это только пример структуры: не подставляй буквальные значения из примера. Не публикуй файл токенов — он содержит секреты.

Если для второго номера уже создана неполная запись с пустым `refreshToken`, сначала сделай резервную копию и удали только запись второго номера. Это можно сделать безопасно так:

```sh
cp -p "$LKDR_TOKENS_FILE" "$LKDR_TOKENS_FILE.bak"
python3 - "$LKDR_TOKENS_FILE" "$LKDR_PHONE_2" <<'PY'
import json, sys
from pathlib import Path

path, phone = Path(sys.argv[1]), sys.argv[2]
data = json.loads(path.read_text(encoding="utf-8"))
if not isinstance(data, dict) or "token" in data:
    raise SystemExit("Ожидался phone-keyed JSON; файл не изменён")
if phone not in data:
    raise SystemExit(f"Запись {phone} не найдена; файл не изменён")
del data[phone]
tmp = path.with_suffix(path.suffix + ".tmp")
tmp.write_text(json.dumps(data, ensure_ascii=False, indent=2) + "\\n", encoding="utf-8")
tmp.chmod(0o600)
tmp.replace(path)
print(f"Удалена только запись {phone}; остальные аккаунты сохранены")
PY
```

После этого запусти программу снова: для второго номера должна начаться полноценная авторизация. Резервную копию не удаляй, пока не убедишься, что оба аккаунта работают.

## Обновление токена из HAR

```sh
python3 ./tools/update_lkdr_token.py "$HOME/Downloads/имя-файла.har" --phone "$LKDR_PHONE"
```

HAR содержит заголовки авторизации и другие чувствительные данные. Не публикуй его и не отправляй посторонним.

Если в HAR найден только истёкший токен, скрипт откажется его сохранять. Скрипт извлекает access token из HAR, но не получает новый refresh token. Поэтому он подходит только для обновления access token при наличии уже сохранённого refresh token; он не предназначен для первичной авторизации второго телефона. Для второго номера не используй этот скрипт как способ создать новую сессию. Отсутствие refresh token означает, что автоматически продлить сессию нельзя.

## Формат экспорта

Для второго телефона задай `LKDR_PHONE_2` и обязательно проверь, что это именно второй аккаунт, а не повтор первого номера. Перед первым запуском второго аккаунта убедись, что `LKDR_TOKENS_FILE` доступен для записи. Если запись второго номера отсутствует, программа должна запросить CAPTCHA и SMS-код второго номера и сохранить его собственную пару токенов.

`LKDR_DEVICE_ID_2` и `LKDR_USER_AGENT_2` необязательны: если их не задавать, используются значения первого аккаунта. Указывай отдельные значения, если второй телефон/браузер имеет другой `sourceDeviceId` или User-Agent. `LKDR_OUTPUT_FILE_2` должен отличаться от `LKDR_OUTPUT_FILE`, иначе программа остановится с ошибкой.

Оба аккаунта обрабатываются последовательно: сначала первый, затем второй. Токены находятся в одном `LKDR_TOKENS_FILE`, но каждая запись привязана к своему номеру телефона. Не используй для второго телефона access/refresh token первого телефона.

**Если появляется `refresh token: validation.failed (Пустой refreshToken)`:** это означает, что для текущего номера в хранилище есть запись без refresh token. Не удаляй весь файл токенов. Сделай резервную копию и удали только запись проблемного номера, после чего повтори запуск и пройди авторизацию именно для него. Существующая запись первого номера при этом должна остаться нетронутой.

При повторном запуске программа продолжает работу по существующим файлам: успешно полученные `fiscalData` не загружаются повторно, а ошибки подробностей пробуются ещё раз. Если список чеков был получен не полностью, он перечитывается с начала с удалением дублей по ключу.

Установка также накладывает исправления кодов ошибок ФД: `receipt.fiscal.data.not.found` распознаётся как отсутствие данных, а `receipt.fiscal.data.invalid.kkt` доступен через `IsInvalidKKT`.

`receipts.json` содержит:
- `listComplete` — полностью ли получен список чеков;
- `detailsComplete` — удалось ли получить подробности каждого чека;
- `receipts[]` — объект `receipt`, `fiscalData` и `detailError` при ошибке получения подробностей.

## Важно

Это комплект изменений поверх текущей ветки `master` upstream-репозитория, а не проверенная сборка под все версии Go. После установки выполни:

```sh
go test ./...
go run ./example
```
